## Problem Statement
Switch hackathon (WeMakeDevs). Build a workflow where an AI agent and the people in a team chat get a real task done together. Judged: 30% use of Switch (is it central, would the project break without it), 25% technical execution (clone and reproduce), 25% creativity/impact (real team problem), 20% presentation (demo video + README). Side tracks: Best Blog, #HowISwitch.

## What Makes This Cool
Most "agent in Slack" demos are one bot answering. This one is a small team in a Discord channel: a triager, a reproducer, a fixer and a skeptical reviewer, each its own Claude Code agent with its own role and context, all reading one shared room log. The reviewer can reject the fixer's patch in-thread, the fixer retries, and a human types `approve` in chat. The reviewer's rejection depends on room context (a constraint a human stated earlier in the thread), which a plain script piping two CLIs does not have. Whether Switch is load-bearing is tested in the spike, not assumed.

## Constraints (confirmed with user)
- Agents available: Claude Code only. No Codex, no OpenCode.
- Chat app: Discord (free, instant server, no workspace approval; chosen on that basis, bridge support to be confirmed in the spike).
- Docker is running on the user's Windows machine; Switch Console installs Windows build.
- Time-boxed hackathon; must be cloneable and reproducible (25% of score).
- Switch ships no agents/models; user brings both. Console runs agents, starts a local server in Docker, connects chat apps.
- Greenfield directory, no existing code.

## Premises
1. HYPOTHESIS, gated on the spike: Switch is structurally necessary (shared room state, role-separated agents, humans in the same thread), not a clever prompt. If the spike shows a plain script or a single agent gives the same result, fall back to Approach A plus a Track 2-style framing, and drop the load-bearing claim from the README.
2. A bug report to reviewed PR is a real, legible team workflow that judges grasp in 30 seconds.
3. A seeded demo repo with a real, reproducible bug beats a toy.
4. The Switch template (triager + repro) is the starting point, so novelty must be beyond it: fixer, adversarial reviewer, human gate.
5. NEW: with Claude Code only, "cross-provider" is off the table. The differentiator becomes role-separated agents that share room context plus a human gate, portable across chat apps. A custom agent speaking the agent protocol (a second provider) is a stretch goal, not a dependency.

## Approaches Considered
### Approach A: Template plus fixer (minimal)
Extend the triager/repro template with one fixer agent. Human reads the patch in chat. Effort S, risk low. Ship this first as the guaranteed submission; weak on creativity alone.

### Approach B: Bug-to-PR room with room-aware adversarial review (recommended)
Agents, all Claude Code: triager (routes, records constraints), repro (smallest failing script), fixer (opens branch/PR), reviewer (skeptical, different instructions, ideally a different Claude model than the fixer if Switch lets you set one). Rejection loops back to the fixer in-thread, capped at 2. Human approve/reject gate in Discord before merge. One YAML so a judge runs it with Console. Effort M, risk Med.

### Approach C: Writers' room for creative work (Track 2)
Rejected: "would it stop working without Switch" is a softer answer and reproducibility is weaker.

## Behavior Spec for Approach B
- **Verification gate (spike, 30 min, first):** in Switch Console confirm (a) Discord bridge works on Windows, (b) four Claude Code agents with distinct instructions in one room, (c) one agent can address another by name in-thread, (d) a human message like `approve` is visible to agents. If (c) fails, fall back to Approach A plus a human-relayed review. The README "Switch is load-bearing" claim is written only after the spike passes.
- **Role separation (replaces cross-provider):** each agent has its own instructions and may only do its own job. Reviewer must not edit code (read and run only). Fixer cannot approve. Triager writes constraints into the room. Enforcement: where Switch/Claude Code lets you set per-agent allowed tools, restrict them (reviewer: read and shell only, no git push, no GitHub token). If per-agent restriction is not available, separation is instruction-only and the README says so. The GitHub token is exposed only to the fixer's environment. The reviewer runs the patch in a throwaway checkout (git worktree or container), never the fixer's working tree. The spike checks which of these are possible.
- **State machine (full table):** states = REPORTED, REPRODUCED, FIX_PROPOSED, REVIEWING, REVIEW_PASSED, APPROVED_PENDING_MERGE, ESCALATED, CLOSED. A rejection counter starts at 0 and counts every reviewer rejection and every human `reject`. On each rejection, test the counter BEFORE incrementing: if counter < 2, increment and return to FIX_PROPOSED; if counter is already 2, go to ESCALATED. So rejections 1 and 2 return to the fixer and rejection 3 escalates.
  - REPORTED -> REPRODUCED when repro posts a failing script and its output (else "cannot reproduce" and tag the human).
  - REPRODUCED -> FIX_PROPOSED when the fixer opens or updates the PR.
  - FIX_PROPOSED -> REVIEWING automatically on each fixer push.
  - REVIEWING -> REVIEW_PASSED when the reviewer accepts (edge-case script and room constraints pass); -> FIX_PROPOSED (or ESCALATED) on rejection per the counter rule.
  - REVIEW_PASSED -> APPROVED_PENDING_MERGE on creator `approve`; REVIEW_PASSED -> FIX_PROPOSED (or ESCALATED) on creator `reject`, per the counter rule.
  - ESCALATED: creator `approve` -> APPROVED_PENDING_MERGE; creator `reject` -> CLOSED (PR closed, room stops).
  - APPROVED_PENDING_MERGE: room posts the PR link; creator `reject` here is allowed and goes to CLOSED; `approve` is a no-op.
  - In every other state (REPORTED, REPRODUCED, FIX_PROPOSED, REVIEWING), `approve` and `reject` are ignored with one short room message "not ready for a decision". Non-creator `approve`/`reject` is ignored silently in all states.
- **Human gate:** only the room creator's Discord user may issue `approve` or `reject <reason>`; agent instructions say to ignore those words from anyone else and to check the author on every one. `approve` makes the room post the PR link and "ready for human merge", and nothing else; the human merges. Agents never merge. Fixer's GitHub token is fine-grained, one demo repo, contents plus pull-requests write. Because contents write allows pushes to main, the demo repo MUST have branch protection or a ruleset on the default branch (no direct pushes, PR required, no bypass for the token); the setup script and README prerequisites state this.
- **Room spend/chatter cap:** each agent is told to reply only when addressed by name or by a state transition; a hard turn limit of 30 agent messages per bug, after which the room posts "turn limit hit" and tags the human. Use Switch spend caps if available.
- **Demo retake:** if the reviewer does not reject on a take, rerun with the seeded obvious-patch hint in the fixer instructions; record multiple takes and use the one that shows the rejection. The README states the take was selected.
- **Reliable rejection beat, room-aware:** the seeded bug has a tempting incomplete fix (the obvious patch passes the reported input but fails an edge case). In the demo, the human states a constraint in the thread before the fix (for example "must stay backward compatible with v1 clients"). The reviewer's instructions require it to check room constraints and run the edge-case script. The smoke script asserts: bug fails before, obvious patch fails the edge case and the constraint check, correct patch passes both. The rejection is likely, not scripted; the README says so.
- **Plain-script comparison:** the README includes a short honest section on what a two-CLI script would lack (shared constraints, human thread, chat portability).
- **Failure handling:** if repro cannot reproduce the bug, the room posts "cannot reproduce" with the script output and tags the human; if an agent times out, the room posts its name and stops, one retry max.
- **Prerequisites in README:** Docker, Switch Console (Windows build, exact version), Claude Code, a Discord server and bot, a fine-grained GitHub token. Time to first working room: under 10 minutes after those are installed; install time excluded.

## Recommended Approach
B on Claude Code only, shipped A-first. It still targets the 30% Switch criterion through shared room state, role separation and the human gate, gives a clean demo arc (report, constraint, repro, fix, rejected, fixed, approved), and fits Track 01 ($2,000). Stretch: add a custom agent over the Switch agent protocol as a second "provider" if time remains.

Full-loop time is measured in the spike and reported in the README as a measured number, not a promise.
